# Reload and update from settings

The settings heading has two top-right icon buttons: Reload plugin and Check for updates. Both have translated tooltips and accessible labels, touch-sized targets on mobile, and a shared busy lock. A pending action displays a loading icon. These controls are outside tab sorting and setting search; merely opening settings never starts maintenance.

An inline status to the right of Check for updates shows the installed version and “Not checked” initially. Explicit checks change it to Checking, No update available, an available version, or Check failed (with error detail in the tooltip). Canceling installation retains the available-version hint; it does not claim the update was installed. Status belongs to this settings page, is announced accessibly, and never starts background networking or writes settings.

Reload drains catalog/settings and pending encounter writes through the plugin's public prepareReload boundary, then uses Obsidian's existing plugin loader to unload/load only this plugin ID. Pending or failed learning-data writes cancel unloading. It does not restart the application, change the enabled-plugin list, install a release or contact the network. It returns to the plugin settings afterward. As with normal plugin unloading, Lexis-owned views/resources can close; reload is not a promise to preserve an active review view.

Check reads the latest stable release from `Heptazero/obsidian-lexis` on GitHub. Equal or older versions do not offer a downgrade or fetch code. A newer release requires all three assets and a matching manifest ID/version; Obsidian API compatibility and desktop-only/mobile flags are checked. The dialog shows current → available version. Cancel, Escape or closing settings before confirmation cannot install code. HTTP errors and a 15-second request timeout are visible failures, not claims that no update exists.

After explicit confirmation, download all three assets before unloading or changing files. Revalidate the downloaded manifest. Write only `main.js`, `styles.css`, `manifest.json` under the conventional installed plugin directory. Settings, tokens, encounters, notes and review histories are not downloaded, overwritten or deleted by this updater. Snapshot the previous code in operation-local memory, not persistent backup files. Download failure changes nothing; write or load failure attempts to restore the old code and loader. A failed restoration is explicitly reported, requiring manual reinstall, never reported as success. Development folders are protected from self-update but remain reloadable.

The reload integration uses Obsidian's internal loader (`unloadPlugin`, `loadPlugin`, `loadManifest`), inspected in the locally installed application, not an invented public SDK method. Unsupported loaders produce a clear error. Native store installation was not reused because its download failures can leave assets partially updated; the updater has its own bounded transaction. It does not evaluate downloaded JavaScript itself; normal plugin execution belongs to Obsidian's loader.

Tests cover numeric version comparison, manual-only networking, compatibility, metadata-only checks, download/write/load failures, in-memory rollback, missing-original-styles cleanup, development path protection and timeout cleanup. The isolated browser fixture checks top-right placement, translated controls, busy locking, confirmation/cancel, no late dialogs and no background network requests. These tests do not prove a real Obsidian/mobile reload or release install; real clicking remains user-operated. No release was installed in the user's active app while developing this feature.
